### 14.4 결과 (Result)

#### htpasswd 인증 round-trip 봉인

- registry:2 의 REGISTRY_AUTH=htpasswd enabled 시 cli mode docker push 가 base64 auths entry 와 bcrypt htpasswd entry 의 정합성으로 통과 — 운영자가 htpasswd file + config.json 의 auths 만 정합성 있게 운영하면 동일하게 동작.
- bonus 401 검증으로 (1) 인증 헤더 부재 / (2) 잘못된 credential 모두 거부 — 운영 환경에서 credential rotation 이 잘못된 경우 alert 신호.
- bonus-A 401 + bonus-B 401 + 정상 credential 통과 의 3가지 동작이 같은 e2e 에서 검증되어, e2e 가 htpasswd 활성화의 모든 경로를 cover.

#### 사전 결함 4건의 운영 의의

- (1) entry key match: 운영자가 `https://registry.example.com` 으로 deploy 시 동일 key (`registry.example.com`) 로 config.json 의 auths entry 가 들어가야 push 동작 — 이번 TASK 의 `localhost:5000` 정렬이 그 운영 pattern 의 e2e 정합성.
- (2) host dir permission: `mktemp` 또는 임의 `/tmp/...` directory 를 K8s secret volume mount 로 대체하면 default 0700 으로 mounter 가 uid mismatch 로 fail — 운영자가 directory mode 에 주의.
- (3) hash format: `htpasswd -nb` (apr1) 가 registry:v2 가 인식하지 않는 hash format — 운영자가 registry 로그의 "authentication failure" 로 만남. 본 TASK 가 `httpd:alpine htpasswd -nbB` (bcrypt) 로 통일.
- (4) dangling source: K8s secret 의 tmpfs / bind mount 가 cleanup 되는 패턴 — 운영 환경에서는 거의 없지만 dev 환경 debug 시 주의.

#### 운영 환경 도입 패턴 (운영 가이드 §6.3)

1. K8s secret 의 htpasswd 파일 (`htpasswd: $(htpasswd -nbB ci-runner "$CI_TOKEN" | base64)`).
2. K8s secret 의 config.json (auths entry + insecure-registries).
3. Runner deploy 의 volumeMount + env (`RUNNER_REGISTRY_CONFIG_DIR=/registry-config`).
4. 동일하게 동작 — 본 TASK 의 e2e 가 secure / mount 자동화의 production 패턴.
