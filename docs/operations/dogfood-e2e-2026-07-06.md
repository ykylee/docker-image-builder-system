## 3. 핵심 관찰

### 3.1 확인된 정상 동작

- Build Monitor 에서 build 상태/phase/logs 가 실제 runner 처리 결과와 일치한다.
- preview service 는 build 완료 후 실제로 떠 있으며 health endpoint 로 확인 가능하다.
- 러너 1대 기준 동시 요청은 queue 에 쌓인 뒤 순차 처리된다.

### 3.2 재현된 이슈

- source upload race:
  - UI 또는 API 로 `POST /builds` 직후 러너가 너무 빨리 claim 하면 `GET /builds/:id/source` 에서 `404 Source archive not found for build.` 로 실패할 수 있다.
  - 실패 build 예시:
    - `d4b86bb8-bfed-47c6-980c-ea4574796b1c`
    - `b20f5746-b71a-4c98-b0af-3ab361786660`
    - `b9d6d047-652a-40f9-93b5-a0c39bc3e3f9`
- admin UI 디자인 메모:
  - admin 페이지는 상단 global header 와 page-level admin tabs 가 함께 보여 navigation hierarchy 가 다소 중첩되어 보인다.
  - Build Request / Build Detail 대비 admin 화면의 밀도와 시각 톤이 다소 달라 일관성 점검 여지가 있다.

## 4. 다음 세션 권장 시작점

1. source archive race 를 줄일 설계 결정:
   - source upload 완료 전 claim 차단
   - build 생성과 source 업로드를 하나의 intake transaction 으로 묶기
   - runner 측 source fetch retry/backoff 강화
2. 러너 2대 이상으로 병렬 claim 이 실제로 되는지 추가 검증
3. admin UI navigation hierarchy / visual consistency 정리
