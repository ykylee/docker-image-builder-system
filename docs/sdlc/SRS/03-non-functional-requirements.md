# SRS 03 - Non-Functional Requirements

- 문서 목적: 기능 외 품질 속성과 운영 기준을 정리한다.
- 범위: 사용성, 추적 가능성, 일관성, 확장성, 운영성
- 대상 독자: 기획자, 설계자, 운영 담당자
- 상태: draft
- 최종 수정일: 2026-07-03

## 1. 사용성

- `NFR-001` 사용자는 Docker 지식을 요구받지 않아야 한다.
- `NFR-002` 사용자 메시지는 상태 코드보다 행동 가능한 설명을 우선해야 한다.

## 2. 추적 가능성

- `NFR-003` 모든 build는 고유 `buildId`로 추적 가능해야 한다.
- `NFR-004` 모든 주요 상태 전이는 DB에 기록 가능해야 한다.
- `NFR-005` 실패 원인을 운영자가 추적할 수 있는 수준의 로그가 남아야 한다.

## 3. 일관성

- `NFR-006` 동일 `userId + appName`에 대해 동시에 하나의 active build만 허용해야 한다.
- `NFR-007` build 상태와 test/deploy 상태는 분리되어 관리되어야 한다.

## 4. 확장성

- `NFR-008` 실행 결과 URL 모델은 host+port에서 path/subdomain 기반으로 확장 가능해야 한다.
- `NFR-009` 단일 Runner 정책은 초기 기본값이지만 향후 다중 Runner로 확장 가능한 모델이어야 한다.

## 5. 운영성

- `NFR-010` 테스트 실행 환경은 만료 또는 교체 정책에 따라 정리 가능해야 한다.
- `NFR-011` 운영 정책이 확정되기 전까지 시스템은 실행 환경 보안과 공개 범위를 문서로 명시해야 한다.
- `NFR-012` 동시에 실행 가능한 테스트 또는 preview service 수는 운영 기준에 따라 제한 가능해야 한다.
- `NFR-013` build queue와 service queue는 서로 독립적으로 관측 가능해야 한다.
