# Step 04 Design 06 - User Messaging And Failure Handling

- 문서 목적: Docker Build Preview Platform MVP의 사용자 안내 메시지와 실패 처리 원칙을 정의한다.
- 범위: 상태 메시지 변환 규칙, preview 안내 방식, 실패 요약 구조, 내부 정보 경계, 다음 조치 패턴
- 대상 독자: 설계자, 구현 담당자, AI 에이전트, 프로젝트 리드
- 상태: draft
- 최종 수정일: 2026-07-02
- 관련 문서: `docs/sdlc/design/03-api-contract-design.md`, `docs/sdlc/design/05-build-and-preview-execution-flow.md`, `docs/sdlc/SRS/06-mvp-must-requirements.md`, `docs/sdlc/SRS/04-policy-and-constraints.md`

## 1. 문서 목표

이 문서는 Build Server와 Runner가 기록한 상태/오류 정보를 사용자와 AI 에이전트가 어떻게 해석하고 전달해야 하는지 고정하기 위한 설계 문서다.

이 문서가 답해야 하는 질문:

- 내부 상태를 사용자 메시지로 어떻게 바꿀 것인가
- preview URL은 어떤 맥락으로 안내할 것인가
- 실패 시 어디까지 설명하고 무엇을 숨길 것인가
- 다음 조치는 어떤 형식으로 안내할 것인가

## 2. 메시지 설계 원칙

- 사용자 메시지는 Docker 내부 용어보다 사용자 행동 중심 표현을 우선한다.
- 상태 코드는 시스템 간 계약용으로 유지하고, 사용자에게는 자연어 설명으로 번역한다.
- 실패 메시지는 "무엇이 실패했는지"와 "다음에 무엇을 하면 되는지"를 함께 제공해야 한다.
- 내부 디버깅 정보는 그대로 노출하지 않고 요약된 원인 설명으로 변환한다.
- AI 에이전트는 Build Server의 구조화된 상태/오류를 소비해 사용자 맞춤 문구를 조립하는 1차 책임을 가진다.

## 3. 메시지 계층 모델

MVP 메시지는 아래 세 계층으로 나눈다.

### 3.1 시스템 상태 계층

- source: `build_request.status`, `build_request.current_phase`, `test_deployment.status`, `error_code`
- 목적: API와 내부 컴포넌트 간 정합성 유지

예시:

```text
BUILDING
TEST_READY
DOCKER_BUILD_FAILED
```

### 3.2 에이전트 해석 계층

- source: 상태 계층 + 실행 맥락 + 사용자 요청 문맥
- 목적: 사용자에게 보여줄 메시지 템플릿 선택

예시:

```text
빌드를 진행 중입니다.
미리보기 환경을 시작하는 중입니다.
앱 실행 준비는 되었지만 확인 중입니다.
```

### 3.3 사용자 메시지 계층

- source: 에이전트 해석 계층
- 목적: 최종 안내 메시지 전달

예시:

```text
배포 요청을 접수했고 지금 이미지를 만들고 있어요.
테스트용 미리보기 주소가 준비됐어요.
빌드가 실패해서 바로 실행되지는 않았어요. Dockerfile과 실행 포트를 먼저 확인해 주세요.
```

## 4. 상태 메시지 변환 규칙

### 4.1 변환 원칙

- 하나의 내부 상태가 하나의 사용자 문장에 고정될 필요는 없다.
- 다만 사용자 행동에 영향을 주는 메시지 의미는 일관되어야 한다.
- `build.status`와 `testDeployment.status`가 동시에 있을 때는 사용자 입장에서 더 가까운 단계를 우선 설명한다.

### 4.2 권장 상태 메시지 매핑

| 내부 상태 | 사용자 메시지 의미 | 안내 톤 예시 |
| --- | --- | --- |
| `QUEUED` | 요청 접수 후 대기 중 | `배포 요청을 접수했고 곧 빌드를 시작할 예정입니다.` |
| `PREPARING` | 빌드 준비 중 | `배포에 필요한 파일을 준비하고 있습니다.` |
| `VALIDATING` | 입력 검증 중 | `실행에 필요한 설정과 파일을 확인하고 있습니다.` |
| `BUILDING` | 이미지 빌드 중 | `앱을 실행 가능한 이미지로 만드는 중입니다.` |
| `IMAGE_BUILT` | 이미지 빌드 완료, preview 준비 전 | `이미지 빌드는 끝났고 미리보기 환경을 준비하고 있습니다.` |
| `TEST_DEPLOYING` + `QUEUED` | preview 서비스 자원 대기 중 | `빌드는 완료되었고 테스트용 미리보기 실행 자리를 기다리고 있습니다.` |
| `TEST_DEPLOYING` + `RESERVED` | preview 자원 예약 중 | `테스트용 실행 자원을 확보하고 있습니다.` |
| `TEST_DEPLOYING` + `STARTING` | preview 시작 중 | `테스트용 미리보기를 실행하는 중입니다.` |
| `TEST_READY` + `READY` | preview 준비 완료 직후 handoff | `테스트용 미리보기 주소를 정리해 전달하고 있습니다.` |
| `COMPLETED` + `READY` | preview 준비 완료 | `테스트용 미리보기 주소가 준비되었습니다.` |
| `FAILED` | 실패 | `배포가 완료되지 않았습니다. 원인을 확인해 수정이 필요합니다.` |
| `CANCELLED` | 취소 | `진행 중이던 배포가 중단되었습니다.` |

### 4.3 active build 응답 메시지

`POST /builds`에서 `accepted=false`인 경우는 오류보다 진행 상황 재안내에 가깝다.

권장 사용자 메시지:

```text
같은 앱의 배포 작업이 이미 진행 중이어서, 새 작업을 만들지 않고 기존 진행 상황을 이어서 확인할게요.
```

메시지 목적:

- 사용자가 중복 요청을 했다는 느낌보다 기존 작업을 이어보는 경험 제공

## 5. preview URL 안내 규칙

### 5.1 안내 시점

- `build_request.status = TEST_READY`
- `test_deployment.status = READY`
- `preview_url` 존재

위 세 조건을 모두 만족할 때 preview 안내를 권장한다.

실제 사용자 노출 시점은 `TEST_READY` 또는 `COMPLETED + READY`를 모두 허용할 수 있다.

### 5.2 안내 구성 요소

- 현재 상태 요약
- preview URL
- 사용 목적 설명
- 만료 또는 교체 가능성 안내

권장 예시:

```text
테스트용 미리보기 주소가 준비되었습니다.
주소: http://preview-host.example.com:38124
이 주소로 현재 앱 동작을 확인할 수 있습니다.
미리보기는 기본적으로 임시 환경이며, 이후 새 배포가 준비되면 교체될 수 있습니다.
```

### 5.3 보안/정책 메모

- preview 인증 정책이 아직 미정이면 "내부 검토용 임시 주소"라는 성격을 함께 안내하는 편이 안전하다.
- URL 자체는 시스템 원문을 유지하되, 사용자는 URL 전략 변경을 의식하지 않아도 되도록 설명은 단순화한다.

## 6. 실패 메시지 설계 원칙

### 6.1 실패 메시지 기본 구조

모든 실패 메시지는 아래 구조를 권장한다.

```text
1. 결과 요약
2. 원인 범주
3. 사용자가 할 수 있는 다음 조치
4. 필요 시 buildId
```

예시:

```text
배포가 완료되지 않았습니다.
앱을 이미지로 만드는 단계에서 문제가 발생했습니다.
Dockerfile과 실행 포트 설정을 먼저 확인한 뒤 다시 요청해 주세요.
필요하면 buildId를 기준으로 상세 로그를 확인할 수 있습니다.
```

### 6.2 실패 메시지에서 피해야 할 것

- raw stack trace 전체 노출
- Docker 내부 stderr를 그대로 복붙
- "알 수 없는 오류"만 단독으로 전달
- 다음 조치 없는 종료 문구

## 7. 실패 유형별 사용자 안내 패턴

### 7.1 입력/준비 실패

대표 오류 코드:

- `SOURCE_ARCHIVE_NOT_FOUND`
- `DOCKERFILE_NOT_FOUND`
- `INVALID_BUILD_INPUT`
- `INVALID_RUNTIME_PORT`

권장 설명 방향:

- 준비한 파일 또는 설정 문제
- 사용자가 비교적 직접 고칠 수 있는 범주

권장 메시지 예시:

```text
배포 준비 단계에서 필요한 파일이나 설정을 확인하지 못했습니다.
Dockerfile 위치와 실행 포트 설정을 먼저 점검한 뒤 다시 요청해 주세요.
```

### 7.2 빌드 실패

대표 오류 코드:

- `DOCKER_BUILD_FAILED`

권장 설명 방향:

- 애플리케이션 의존성 또는 Docker 빌드 과정 문제
- 로그 확인이 도움될 수 있음을 함께 안내

권장 메시지 예시:

```text
앱 이미지를 만드는 단계에서 문제가 발생했습니다.
의존성 설치나 빌드 명령이 실패했을 가능성이 있으니 build 로그를 함께 확인해 주세요.
```

### 7.3 preview 실행 실패

대표 오류 코드:

- `PREVIEW_PORT_UNAVAILABLE`
- `PREVIEW_CONTAINER_START_FAILED`
- `PREVIEW_HEALTHCHECK_FAILED`

권장 설명 방향:

- 앱 이미지 자체는 만들어졌을 수 있지만 실행 검증 단계가 실패한 상황
- 사용자는 앱 실행 설정과 포트 노출 상태를 의심할 수 있어야 한다.

권장 메시지 예시:

```text
이미지는 준비됐지만 테스트용 미리보기를 실행하는 단계에서 문제가 발생했습니다.
앱이 지정한 포트에서 정상적으로 실행되는지와 시작 시간이 너무 길지 않은지 확인해 주세요.
```

## 8. 내부 정보와 사용자 정보의 경계

### 8.1 사용자에게 직접 보여줄 수 있는 정보

- build 진행 상태
- preview URL
- 오류의 범주화된 요약
- 사용자가 시도할 다음 조치
- 필요 시 `buildId`

### 8.2 기본적으로 직접 노출하지 않는 정보

- container reference
- 내부 host 선택 로직
- raw Docker daemon 오류 전문
- object storage reference
- 내부 파일 시스템 경로

### 8.3 운영자/에이전트 전용 정보

- 전체 `build_log`
- `error_code`
- `current_phase`
- `test_deployment.health_status`
- infra 원인 추적용 상세 로그

설계 메모:

- MVP에서는 API가 운영자/에이전트 친화적으로 설계되고, 최종 사용자 경험의 안전한 축약은 Skill/MCP 계층이 담당하는 모델이 적절하다.
- build queue와 preview service queue를 분리한 경우에도 최종 사용자는 두 내부 큐를 구분해 이해할 필요는 없다.

## 9. 다음 조치 안내 규칙

다음 조치는 오류 유형별로 아래 우선순위를 따른다.

### 9.1 사용자 수정 가능 항목 우선

- `Dockerfile` 위치 확인
- 실행 포트 설정 확인
- 앱 빌드 명령/의존성 점검

### 9.2 재시도 안내

- 일시적 preview 실행 실패로 보이면 재시도를 제안할 수 있다.
- 단, active build 정책상 기존 실패 build가 terminal 상태인지 먼저 확인해야 한다.
- preview service queue 대기 상태는 실패가 아니므로 재시도보다 "대기 중" 안내를 우선한다.

### 9.3 운영자 확인 유도

- 인프라 또는 정책성 이슈로 보이면 사용자가 혼자 해결하기 어려움을 명시한다.

권장 예시:

```text
문제가 계속되면 buildId를 기준으로 운영자 또는 에이전트가 상세 로그를 확인해야 합니다.
```

## 10. 메시지 생성 책임 분담

### 10.1 Build Server 책임

- 구조화된 상태와 오류 코드 제공
- 최소 공통 메시지 필드 제공 가능
- 사용자 친화 문장까지 완전히 책임지지는 않음

### 10.2 Runner 책임

- 실패 단계와 실행 로그를 충분히 남김
- 오류를 분류 가능한 코드로 기록

### 10.3 Skill/MCP 또는 AI 에이전트 책임

- 사용자 문맥에 맞춘 최종 문장 조립
- 중복 build 응답을 자연스럽게 설명
- preview 안내와 실패 후속 행동 제안

## 11. 미결정 항목과 설계 영향

- `OI-005 preview 인증 정책`
  - preview URL 안내 문구와 접근 방법 설명에 직접 영향이 있다.
- `OI-010 preview concurrency limit and queue policy`
  - preview 대기 메시지와 예상 안내 패턴에 직접 영향이 있다.
- `OI-008 Dockerfile 생성 정책`
  - 입력 실패를 수정 안내로 끝낼지 자동 보정 안내로 바꿀지에 영향이 있다.
- `OI-009 실패 요약 생성 책임`
  - 서버 기본 메시지와 에이전트 최종 메시지의 경계에 직접 영향이 있다.

## 12. Step 04 마무리 메모

- Step 04의 여섯 개 설계 문서는 시스템 경계, 상태 모델, API 계약, 데이터 모델, 실행 흐름, 사용자 메시지 규칙을 각각 분리해 고정한다.
- 남은 작업은 미결정 항목의 우선 의사결정과 설계-요구사항 traceability 표기 규칙 정리다.

## 13. 현 단계 결론

- MVP 사용자 경험의 핵심은 상태를 정확히 기록하는 것만이 아니라, 그 상태를 사용자가 이해하고 다음 행동을 선택할 수 있는 문장으로 바꾸는 것이다.
- 실패 처리는 내부 상세 정보를 안전하게 숨기면서도, 원인 범주와 다음 조치를 분명히 안내하는 구조가 적절하다.
