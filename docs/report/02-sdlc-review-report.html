요구사항 정리, 설계 세분화, 리뷰, 문서 정합성 보정을 거친 현재 기준에서 왜 지금 구현에 들어갈 수 있는지, 어떤 순서로 시작해야 하는지를 과제 기획안 관점으로 정리한 문서다.

기준 시점: 2026-07-03 현재 focus: TASK-017 다음 착수: shared package 또는 API scaffold
Proposal Summary
Build Server P0 선착수

공통 계약과 API 뼈대를 먼저 여는 방식이 현재 문서 기준선과 가장 잘 맞고, 이후 재작업 비용도 가장 낮다.

Immediate Focus
TASK-017

문서 정합성 보정 이후 첫 코드 진입점으로 scaffold 착수가 대기 중이다.

기획 판단: 남은 핵심 과제는 설계 추가 생산이 아니라, 현재 기준선을 손상시키지 않는 첫 구현 진입 순서를 선택하는 일이다.

Why Now

왜 지금 구현 착수가 가능한가

이번 기획안은 리뷰 결과를 그대로 나열하지 않고, 이미 보정이 끝난 상태를 기반으로 다음 행동을 제안한다.

Reason 01

요구사항과 설계가 닫혀 있다

MVP 범위, 상태 모델, preview 정책, 공통 계약, Build Server P0 구현 축이 단계별 문서로 연결되어 있다.

구현자가 무엇을 기준으로 시작해야 하는지가 문서에 남아 있다.

Reason 02

정합성 보정이 끝났다

`TEST_READY`, preview `QUEUED`, 저장소 준비도, workflow 메타 문서명 혼선이 정리되었다.

즉, 현재는 “무엇이 진짜 기준인가”를 다시 묻지 않고 착수할 수 있다.

Reason 03

다음 작업이 하나로 좁혀졌다

이제 남은 선택지는 shared package scaffold와 Build Server API scaffold의 순서 문제다.

즉, 설계 탐색 단계가 아니라 구현 진입 전략 단계다.

Goal

이번 과제의 목표

이번 기획안의 목표는 Build Server MVP를 가장 안정적으로 구현 착수 가능한 구조로 여는 것이다.

Goal 01

문서 기준선 보존. 구현이 요구사항과 설계 문서를 거스르지 않도록 source-of-truth를 유지한다.

Goal 02

Build Server P0 우선 착수. `PKG-001`~`PKG-004`를 코드 scaffold와 초기 구현 단위로 연결한다.

Goal 03

재작업 최소화. 공통 계약과 DB 경계를 먼저 고정해 이후 API, Runner, Skill/MCP가 같은 기준 위에 올라가게 한다.

Goal 04

후속 결정 통제. medium decision은 실제 차단점이 생길 때만 선택적으로 닫아 일정 확장을 막는다.

Scope

1차 수행 범위

이번 과제의 1차 범위는 Build Server P0를 코드 구조로 여는 것이며, Runner 전체 구현은 후속 범위로 둔다.

P0 · Build Server

포함 범위

  • `packages/shared-contract`
  • `packages/shared-config`
  • `packages/db`
  • `apps/build-server` bootstrap
  • `POST /builds`, `GET /builds/{buildId}`, `GET /builds/{buildId}/logs` 진입 구조
Later · Follow-up

후속 범위

  • Runner claim/execute loop 전체 구현
  • reverse proxy 기반 preview URL 확장
  • registry push / deployment registration
  • `OI-006`, `OI-008`, `OI-009`의 전면 정리

범위 원칙: 사용자 가치와 직접 연결되는 Build Server P0부터 열고, 운영 확장과 후속 자동화는 다음 단계로 넘긴다.

Plan

추진 단계

기획상 가장 안정적인 추진 순서는 shared package 선착수, API 진입 구조 확장, persistence 연결 순서다.

Phase 1

shared package scaffold

먼저 `packages/shared-contract`, `packages/shared-config`, `packages/db`를 만들고 enum, schema, config entry를 배치한다.

Phase 2

Build Server API shell

`apps/build-server`에 Fastify bootstrap, route registry, Zod schema 연결 구조를 생성한다.

Phase 3

persistence baseline

`build_request`, `build_log`, `test_deployment` schema와 migration, repository contract를 연결한다.

Phase 4

selective decision closure

구현 차단이 생길 때만 `OI-006`, `OI-008`, `OI-009`를 선택적으로 닫아 일정 확장을 통제한다.

Deliverables

기대 산출물

이번 기획안에 따라 착수할 경우 산출물은 문서가 아니라 실제 저장소 구조와 실행 가능한 초기 코드가 된다.

Output 01

shared package scaffold와 공통 타입, enum, schema 진입점

Output 02

Build Server API shell과 route, schema, service 기본 골격

Output 03

DB schema 및 migration baseline, repository contract 초안

Output 04

개발 기본 명령 정의와 이후 Runner 확장에 필요한 초기 실행 기준

Risk

주요 리스크와 대응

현재 리스크는 설계 부족보다 구현 초반 경계 설정 실패에 가깝기 때문에, 대응도 범위 통제와 기준 유지에 집중한다.

Risk 01

패키지 경계 혼선. `PKG-001`~`PKG-004` 문서와 1:1 대응되는 디렉터리 책임을 먼저 고정한다.

Risk 02

후속 decision 확장. `OI-006`, `OI-008`, `OI-009`는 실제 차단점이 생길 때만 닫는다.

Risk 03

실행 기준 부재. scaffold와 동시에 기본 `install`, `run`, `test` 명령을 정의한다.

Conclusion

기획 결론

핵심 제안

이번 과제는 Build Server P0를 중심으로 shared package와 API scaffold를 먼저 여는 방향으로 추진하는 것이 가장 적절하다.

기대 효과

문서 기준선의 강점을 그대로 코드 구조로 옮길 수 있고, 이후 Runner와 운영 확장도 더 낮은 비용으로 이어갈 수 있다.

제안 문장: “문서 정합성 보정이 마감된 현재 시점에서, Build Server P0 구현을 위한 shared package 및 API scaffold 착수를 1차 과제로 추진한다.”
