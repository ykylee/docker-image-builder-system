Overview

프로젝트 개요

이 프로젝트는 AI 앱 제작 흐름의 마지막 병목인 “실행 가능한 테스트 환경 확보”를 해결하기 위한 플랫폼이다.

사용자
비개발자

Dockerfile, 이미지 빌드, 포트 설정을 몰라도 배포를 요청할 수 있어야 한다.

입력
자연어

사용자는 AI 에이전트에게 “배포해줘”라고 말하는 수준의 경험을 기대한다.

핵심 처리
Build + Preview

빌드 성공보다 테스트 가능한 preview URL 제공이 더 중요하다.

현재 상태
설계 완료

요구사항과 설계 정리까지 끝났고, 이제 구현 스캐폴드를 여는 단계다.

핵심 메시지: 이 프로젝트는 Docker 도구가 아니라, AI가 만든 앱을 누구나 실제로 실행해보게 만드는 마지막 연결 고리다.

Flow

사용자에게 보이는 서비스 흐름

리더에게는 기술 설명보다 “요청이 어떻게 결과로 바뀌는가”가 먼저 보여야 한다.

Step 01

사용자 요청

사용자가 AI 에이전트에게 배포를 요청한다.

Step 02

AI 에이전트 준비

앱 산출물과 Docker 준비물을 점검하고 전달 형식을 맞춘다.

Step 03

Build Server 접수

빌드 요청을 저장하고 상태, 로그, 중복 요청을 관리한다.

Step 04

Runner 실행

실제 Docker 이미지 빌드와 preview 실행을 수행한다.

Step 05

결과 반환

사용자는 preview URL 또는 실패 안내를 받는다.

핵심 포인트: 사용자는 Docker 절차를 보지 않는다. 시스템이 복잡성을 숨기고 결과만 preview URL로 돌려준다.

Architecture

시스템 구성

구성은 단순하다. 사용자 접점은 AI 에이전트가 맡고, 실제 빌드와 실행은 서버 쪽으로 분리한다.

Front Layer

Skill / MCP

요청 해석, 앱 산출물 준비, Build Server 호출, 상태 안내를 담당한다.

User Value

쉬운 배포 경험

비개발자도 인프라 지식 없이 테스트 URL을 받을 수 있어야 한다.

Core Hub

Build Server

모든 요청과 상태를 중앙에서 관리하는 운영 허브

Request Intake

빌드 요청 수신과 active build 중복 방지

Status Tracking

상태, 로그, 메타데이터 저장과 조회

Queue Coordination

Runner가 소비할 작업 단위 관리

Preview Metadata

preview URL과 테스트 실행 결과 정리

Execution Layer

Runner

`docker build`, `docker run`, 로그 적재, preview 수명 관리의 실행 주체다.

Outcome

Preview URL

최종 결과물은 기술 로그가 아니라 사용자가 눌러볼 수 있는 실행 링크다.

Why It Matters

왜 필요한가

이 프로젝트는 기술 탐색이 아니라 AI 제품 경험을 완성하기 위한 운영 인프라 투자에 가깝다.

문제 01

AI가 앱을 만들어도 바로 검증하기 어렵다. 결과물을 실행해볼 환경이 없으면 사용자 신뢰가 떨어진다.

문제 02

비개발자에게 Docker는 너무 어렵다. 빌드와 실행의 복잡성은 시스템이 흡수해야 한다.

문제 03

운영 책임 분리가 필요하다. 요청 해석, 상태 관리, 실제 실행을 나누지 않으면 확장성과 안정성이 떨어진다.

기대 효과

“만들었다”에서 “실행해봤다”로 전환된다. AI 앱 제작 경험이 실제 서비스 경험으로 올라가는 변화다.

Scope

1차 구현 범위

처음부터 모든 것을 만들지 않는다. 사용자 가치와 직접 연결되는 Build Server P0를 먼저 만든다.

Priority Scope

이번에 먼저 만드는 것

  • 공통 계약 패키지 `packages/shared-contract`
  • 공통 설정 패키지 `packages/shared-config`
  • DB 계층 패키지 `packages/db`
  • `apps/build-server` 초기 API 골격
  • `POST /builds`, `GET /builds/{buildId}`, `GET /builds/{buildId}/logs`
Deferred Scope

다음 단계로 미루는 것

  • 다중 Runner 병렬 처리
  • reverse proxy 기반 preview 라우팅 확장
  • registry push / deployment registration
  • 운영 미결정 항목 전면 정리

범위 전략: 먼저 빌드 요청, 상태 관리, preview 연결의 최소 구조를 만들고 이후 운영 확장을 붙인다.

Roadmap

추진 단계

지금은 설계를 더 늘리기보다, 정리된 설계를 안전하게 코드 구조로 옮기는 순서가 중요하다.

Phase 1

공통 기반 스캐폴드

`shared-contract`, `shared-config`, `db` 패키지를 먼저 열어 타입, enum, schema 진입점을 고정한다.

Phase 2

Build Server API 진입 구조 생성

Fastify bootstrap, route, schema, service, repository 뼈대를 만들어 서버 책임을 명확히 한다.

Phase 3

Persistence baseline 연결

`build_request`, `build_log`, `test_deployment` 기준으로 migration과 repository contract를 연결한다.

Phase 4

Runner 및 운영 정책 확장

필요할 때만 preview queue, Runner claim, 후속 의사결정 항목을 닫아 확장한다.

Deliverables

예상 산출물

이 프로젝트는 문서만 쌓는 과제가 아니라, 실제 저장소 구조와 구현 시작점을 만드는 과제다.

Output 01

기획 산출물

프로젝트 소개 자료, 기획안, SDLC 기준 문서 세트

Output 02

설계 산출물

상태 전이 모델, 시스템 책임 분리, API 계약 초안, 데이터 모델 기준

Output 03

구현 산출물

shared packages, Build Server API shell, migration baseline, repository 기본 구조

Output 04

운영 산출물

다음 단계 backlog, 기본 실행 명령, Runner 확장 진입 기준

Risk

주요 리스크와 대응

현재 리스크의 본질은 기술 난이도보다 “무엇을 먼저 고정할 것인가”에 있다.

Risk 01

패키지 경계 혼선. `PKG-001`~`PKG-004`와 코드 디렉터리 책임을 1:1로 대응시켜 방지한다.

Risk 02

미결정 항목 확장. 운영 정책은 구현 차단점이 생길 때만 닫아 일정 확대를 막는다.

Risk 03

실행 기준 부재. 스캐폴드와 함께 기본 `install`, `run`, `test` 명령을 정의한다.

Conclusion

의사결정 포인트

리더에게 필요한 것은 설계 상세가 아니라, 지금 무엇을 승인하면 되는지다.

“지금은 추가 기획보다, 정리된 기준선 위에서 Build Server P0 구현을 시작할 시점이다.”

1

프로젝트 목적은 명확하다. AI가 만든 앱을 실제로 실행해보게 만드는 것이다.

2

구성은 단순하다. AI 에이전트, Build Server, Runner의 책임이 구분되어 있다.

3

범위는 통제되어 있다. Build Server P0부터 시작하고 후속 확장은 단계적으로 진행한다.

4

다음 행동은 분명하다. shared package와 API scaffold를 먼저 연다.

제안 문장: Docker Image Builder System의 1차 구현 범위를 Build Server P0 중심으로 승인하고, 공통 패키지와 API 스캐폴드 착수를 즉시 진행한다.

에셋 메모: 본 자료의 아이콘과 도식은 모두 HTML 내부 SVG와 CSS로 포함되어 있어, 외부 네트워크 없이 오프라인에서도 동일하게 동작한다.
